# 部门权限与自动营销改造

工作台入口：`/workspace`。所有新业务操作经 JWT 校验，并重新读取账号、部门和角色状态。普通成员只能使用工作台 API；原管理后台、文件、AI 配置、Docker、邮箱密码和系统服务等旧接口保留给超级管理员，避免旧 SQL 缺少部门条件造成越权。

## 组织与数据

- 原账号、角色继续使用；增加部门树和角色数据范围。数据范围与授予该操作的角色绑定，防止多个角色组合后权限扩大。
- 范围：本人、本部门、本部门及下级、指定部门、全部。超级管理员保留系统权限。
- 联系人组、联系人、标签、模板、营销任务及原 API 配置增加 `dept_id/owner_id`。原数据归入默认部门和原管理员。
- 分组、模板名称调整为部门内唯一。员工调部门不自动迁移历史数据；旧任务会因负责人归属不匹配暂停发送。
- 邮箱授权与角色权限分开：普通员工必须同时具备发布权限和部门邮箱授权。
- 角色、账号修改提高 token_version；账号或部门停用、权限和邮箱授权撤销会影响后续请求及后台发送。
- 管理员初始化只在首次创建时使用环境变量密码，重启不再覆盖已经设置的管理员密码。
- 组织资源采用停用保留审计；任务取消保留明细。

## 发送与调度

- 现有群发任务、API 邮件由统一持久化调度执行；旧线程速度不是发信上限。
- 公平顺序为部门最近调度时间、任务优先级、任务最近调度时间。工作池本地最多32个执行单元；全系统默认最多8个同时提交。
- 每个任务独立设置：分钟、小时、24小时滚动上限；相邻提交最小间隔；并发；批次数量及批间休息；收件人触达间隔；时区、星期和每日时间窗。
- 系统、部门、邮箱、IP、服务商和任务的限制同时生效。0只取消当前层的额外限制，不覆盖上层限制。
- 配额和间隔通过 PostgreSQL 事务及 advisory lock 原子预留。所有实例共享限制；拒绝时不会部分消耗其他范围的额度。计数按提交预留尝试保守计算，失败不自动返还。
- 收件人触达间隔按部门和规范化邮箱地址计算；如需跨部门公司级限制，应改为统一作用域。
- 任务以 `FOR UPDATE SKIP LOCKED` 原子领取，带唯一租约令牌。未进入 SMTP 的过期领取可恢复；SMTP 状态不确定时进入 unknown，由管理员核对，避免盲目重发。
- SMTP accepted 仅表示邮件服务器接受，最终投递状态继续依靠原 Postfix 日志统计。应用的发送间隔不等于外网投递间隔。
- 暂停、取消只停止后续提交，已进入 Postfix 的邮件可能继续投递。
- 发件IP及服务商预热沿用原有实现。建议配置IP范围策略前先在实际部署环境核对检测到的出口IP。

## 计划与自动化

- 支持一次、每天、每周和每月计划，按本地时区计算。月底不足指定日期时采用最后一天。
- 每次执行生成独立任务和运行记录；服务停机后最多补一次，同一计划已有未完成任务时跳过重叠执行。
- 支持结束时间和最大执行次数。计划校验失败会停用并显示错误，不循环重试创建失败任务。
- 自动化是订阅确认触发的顺序规则：等待、始终发送、前一封已打开、已点击或未打开。不是任意节点画布。
- 仅纳入规则创建后新确认的联系人；已有订阅者不会被自动补纳入。导入为已确认的联系人也会触发启用的规则，导入前应明确是否需要营销。
- 每个联系人执行实例保留规则配置快照，修改规则影响新加入的联系人。打开、点击属于观测信号，可能受到代理或扫描影响。
- 每封营销邮件包含退订链接，发送前重新检查联系人是否仍已确认并处于订阅状态。

## 构建与部署

开发依赖：Go 1.23.2、Node.js 22、pnpm 11。前端依赖的生命周期脚本在 pnpm-workspace.yaml 显式列出。Windows 中 ssh2 的可选加速绑定缺少编译器时可降级，实际前端构建结果单独验证。

```sh
cd core/frontend
pnpm install --frozen-lockfile
pnpm build
```

在 Linux / Docker 环境构建自定义版本，不要仅拉取上游 core 镜像，否则本地修改不会生效：

```sh
docker compose -f docker-compose.yml -f docker-compose.enterprise.yml build core-billionmail
docker compose -f docker-compose.yml -f docker-compose.enterprise.yml up -d
```

正式升级前应保存数据库、配置、邮箱文件和原镜像。`governance/migration.sql` 在基础表初始化后通过事务执行，失败阻止启动，重复执行保持兼容。停止旧 core 实例后再切换新版本，不允许新旧调度器同时发送。

自定义版本后续更新继续使用 enterprise 编排与自定义镜像。不要直接使用上游 `bm update` 替换正在运行的 core，否则可能恢复到没有部门访问边界的官方版本。

回滚优先恢复完整升级前备份。若只回退旧应用而保留新增部门账号，必须先停用新增的非管理员账号和API凭证：旧应用没有新的部门访问边界，不能保持这些账号在线。

首次配置顺序：部门 → 角色与范围 → 员工 → 邮箱授权 → 共享发送策略 → 联系人及模板 → 草稿 → 发布。计划和自动化创建者还需拥有创建、发布任务以及读取受众和模板的权限。

## 验证

Go 测试在 `governance`、`batch_mail`、`enterprise` 中。集成测试仅在指定 BM_TEST_PG_HOST 后执行，会创建独立 bm_test_* 数据库并清理，不复用正式业务库。

```sh
BM_TEST_PG_HOST=127.0.0.1 BM_TEST_PG_PORT=5432 BM_TEST_PG_PASSWORD=... \
  go test ./internal/service/governance ./internal/service/batch_mail ./internal/controller/enterprise
```

生产验收还应覆盖目标服务器迁移、全组件联调、真实邮箱投递与收件确认；构建通过不代替这些验收。

本地验证范围包括：部门列表、更新、删除、导出及创建权限隔离；公开旧接口的HTTP访问边界；共享滚动配额、并发与批间休息；收件人触达间隔；重复迁移；并发领取；SMTP不确定结果恢复；月末与夏令时计划；计划防重复；订阅触发及点击条件序列；API队列防重复；JWT撤销和算法限制。SMTP测试使用本地测试服务接收完整邮件，不代表公网邮箱收件已验证。
